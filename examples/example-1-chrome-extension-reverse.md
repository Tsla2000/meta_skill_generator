# 验证样例 1：技术逆向类

生成器输入：`浏览器扩展逆向`
验证点：主类型是软件分析加迁移复刻。骨架是 manifest 先行、权限核销、注入面追踪，与样例 2 的数据核验骨架完全不同构，证明不是换名模板。

---

# 专用 Skill：Chrome 扩展逆向与功能复刻

## 目标
拿到一个 Chrome 扩展的安装包或已解压目录，还原它向页面注入了什么、在后台做了什么、数据流向哪里，并把其中一个指定功能用原创代码复刻出来。完成标志：机制报告每条结论有文件与行号级证据，复刻功能在本地测试页上行为与原扩展一致。

## 对象与范围
- 对象：用户提供或有权分析的扩展（CRX、zip 或已解压目录），记录版本与来源。
- 包含：manifest 声明、content script、service worker、popup 与 options 页、扩展与页面的消息通道。
- 排除：绕过付费许可、提取他方密钥、复刻其商标与图标素材。

## 开工前检查
- [ ] 目标可解压：CRX 先剥头再按 zip 解开，解不开就停下报告文件类型实测结果，不猜。
- [ ] 记录基线：文件清单、总大小、manifest 版本（MV2 或 MV3），后续结论都引用这份基线。

## 执行阶段
### 阶段 1：manifest 先行
- 做：逐字段读 manifest.json，列出 permissions、host_permissions、content_scripts 的 matches 与 run_at、background 入口、web_accessible_resources。
- 判：这张表是能力上限，不是已用能力。每项权限留到阶段 2 核销，核销不掉的标「声明未用」。
- 产出：`manifest-map.md`，每行一项声明加对应代码位置（待核销先空着）。
### 阶段 2：权限核销与注入面追踪
- 做：全文检索每个权限对应的 API 调用。从 content script 入口追 DOM 读取与修改、事件监听、向后台的消息名与载荷结构。
- 判：追不到调用的权限不许写进机制结论。消息通道要追到接收端才算闭合，只见发送不见接收的标未闭合。
- 产出：注入面清单加消息通道表（发送方、消息名、载荷、接收方）。
### 阶段 3：后台与网络面
- 做：读 service worker 的 fetch 拦截、alarms、storage 读写键名。检索全部出站域名，与阶段 1 的 host_permissions 对照。
- 判：代码里出现的域名超出声明范围的，单独标红，这是扩展商店审核与隐私判断的关键点。
- 产出：网络面表（域名、触发动作、发送的数据类型）。
### 阶段 4：单功能复刻
- 做：只选用户指定的一个功能，用原创代码在本地测试页实现其可观察行为，行为规格只取阶段 1 到 3 的已验证结论。
- 判：测试页上同一组输入，原扩展与复刻版的可观察输出逐项对照，全对才算复刻成立。
- 失败时：对照不一致先回查行为规格是否漏了条件，不许靠改测试用例凑过。

## 证据规范
- 每条机制结论标注等级并附文件路径与行号或检索式。压缩混淆导致读不出的模块，写明混淆形态并降级为行为推断，禁止把推断写成源码事实。

## 禁止与避坑
- 把 manifest 权限直接当作功能清单，是本领域第一大错。权限是上限，必须代码核销。
- 不要把 popup 页的逻辑当作扩展主逻辑。MV3 的重心在 service worker 与 content script。
- 不要在用户主力浏览器配置里装来路不明的 CRX 实测。用隔离配置加载解压版观察。

## 交付物
- `REPORT.md`：manifest 映射、注入面、消息通道、网络面、复刻对照结果、未知清单。

## 验收标准
- [ ] manifest 每项声明都有核销结果（已用位置或声明未用）。
- [ ] 每条出站域名都能在代码中找到触发点。
- [ ] 复刻功能对照表逐项通过，或未通过项写明差异与原因。
